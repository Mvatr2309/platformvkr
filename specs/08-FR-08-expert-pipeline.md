# FR-08: Экспертная труба

Раздел, в котором студент находит эксперта с валидным опытом и записывается к нему на консультацию. Запрос проходит двойную проверку — модератор, затем эксперт, — после чего стороны обмениваются контактами. Через 7 дней система собирает обратную связь с обеих сторон.

**Статус документа:** согласован по архитектуре и доступам. Состав полей карточки эксперта и анкеты запроса — черновик, помечен «требует подтверждения» (см. раздел 11).

## 2. Роли и доступы

| Роль | Как получает доступ к трубе | Что делает |
|------|------------------------------|------------|
| Админ (`ADMIN`) | Всегда, без условий | Модерирует запросы, приглашает внешних экспертов, открывает когорты, смотрит метрики |
| Научный руководитель (`SUPERVISOR`) | Сам нажимает «Принять участие в роли эксперта» | Размещает карточку, принимает и отклоняет запросы |
| Внешний эксперт (`EXPERT`) | Аккаунт создаёт админ из админки трубы | То же, что НР-эксперт. Доступа к «Платформе ВКР» нет |
| Студент (`STUDENT`) | Когорта студента отмечена админом как открытая | Смотрит каталог, отправляет анкету, оставляет обратную связь |

**Модератор — это существующая роль `ADMIN`.** Новой системной роли модератора не появляется.

**Роль эксперта не хранится в поле `User.role`.** Поле одно и у научного руководителя занято значением `SUPERVISOR` — перезапись отрежет его от научного руководства. Признак роли эксперта — наличие записи `ExpertProfile` у пользователя. Значение `EXPERT` в перечислении `Role` нужно только для внешних экспертов, у которых нет другой роли на платформе.

Выхода из роли эксперта нет. Если эксперт больше не хочет получать запросы, он скрывает карточку (08.09).

## 3. Навигация и пространства

### 3.1 Экран выбора

Новая страница `/spaces` — две плитки. Авторизованный пользователь, открывший корень сайта, попадает на неё; неавторизованный видит текущий лендинг. Редирект после логина ведёт туда же вместо текущей развилки по ролям.

Последний выбор не запоминается — плитки показываются при каждом заходе на сайт.

Название раздела на плитке и в интерфейсе — «Экспертная труба», одинаково для всех ролей, включая студентов.

Переход по прямой ссылке (письмо, in-app уведомление, закладка) экран выбора не показывает и ведёт на целевую страницу.

### 3.2 Состояния плиток

| Кто смотрит | «Платформа ВКР» | «Экспертная труба» |
|-------------|------------------|---------------------|
| Админ | Открыто | Открыто |
| НР с ролью эксперта | Открыто | Открыто |
| НР без роли эксперта | Открыто | **Приглашение** — «Принять участие в роли эксперта» |
| Студент из открытой когорты | Открыто | Открыто |
| Студент из закрытой когорты | Открыто | **Замок**, некликабельна |
| Внешний эксперт | **Замок**, некликабельна | Открыто |

Плитка с замком не кликается — ни тултипа, ни модалки. Прямой переход по URL закрытого пространства отдаёт заглушку, а не 404.

### 3.3 URL

Труба живёт под префиксом `/expert/*` — отдельная route-группа со своим лейаутом и сайдбаром. Контекст пространства определяется URL, а не cookie: иначе ломаются диплинки из писем, открытие в новой вкладке и кнопка «назад».

**«Платформа ВКР» остаётся на текущих URL без префикса.** Полная симметрия, о которой договорились, — это симметрия интерфейса и админки, но не адресов: перевод платформы на `/vkr/*` сломал бы все существующие ссылки в отправленных письмах, уведомлениях и закладках пользователей.

| URL | Кому | Назначение |
|-----|------|------------|
| `/spaces` | всем авторизованным | Экран выбора пространства |
| `/expert` | студент / эксперт | Точка входа: каталог для студента, кабинет для эксперта |
| `/expert/catalog` | студент | Каталог карточек, фильтр по темам |
| `/expert/catalog/[id]` | студент | Карточка эксперта, кнопка «Оставить запрос» |
| `/expert/requests/new?expertId=` | студент | Анкета запроса |
| `/expert/my-requests` | студент | Мои запросы со статусами и причинами отказа |
| `/expert/my-requests/[id]/feedback` | студент | Форма обратной связи |
| `/expert/inbox` | эксперт | Входящие запросы, принять / отклонить |
| `/expert/inbox/[id]/feedback` | эксперт | Форма обратной связи |
| `/expert/profile` | эксперт | Карточка эксперта, скрытие карточки |
| `/expert/join` | НР без роли эксперта | Подключение роли |
| `/expert/admin/requests` | админ | Очередь модерации |
| `/expert/admin/access` | админ | Открытые когорты |
| `/expert/admin/invitations` | админ | Приглашение внешних экспертов |
| `/expert/admin/metrics` | админ | Конверсия запрос → встреча |

### 3.4 Подключение роли без повторного входа

Механика уже обкатана в проекте на сохранении профиля (`app/profile/page.tsx` → `updateSession()` → ветка `trigger === "update"` в `lib/auth.ts`):

1. НР нажимает «Принять участие» на `/expert/join`.
2. `POST /api/expert/join` создаёт `ExpertProfile`, предзаполняя из `SupervisorProfile` фото, место работы, должность, звание, степень, резюме, экспертизу, направления и типы проектов. Дальше карточка правится отдельно от профиля НР.
3. Клиент вызывает `updateSession()`.
4. Ветка `trigger === "update"` в `jwt`-колбэке перечитывает из БД признак роли эксперта — сейчас она перечитывает только `profileCompleted` и `name`, её надо расширить.
5. Плитка разблокирована, пользователь внутри трубы.

Роль пускает в пространство сразу, но **в каталог карточка попадает только после заполнения обязательных полей**. До этого эксперт видит у себя баннер «заполните карточку, чтобы вас нашли».

## 4. Доступ студентов по когортам

Когорты — существующий справочник `cohorts` («Потоки»), который админ правит в `/admin/dictionaries`. Когорта присваивается студенту при создании аккаунта и уже обязательна.

Отдельной «даты открытия раздела» нет: галочка у когорты и есть механизм открытия, вторая правда в этом вопросе не нужна.

**Правила:**

- Труба открыта студенту, если значение его `StudentProfile.cohort` отмечено как открытое.
- Пустая когорта = доступа нет. В админке трубы выводится счётчик «студентов без потока: N», чтобы такие студенты не потерялись молча.
- Проверка когорты обязательна и на страницах `/expert/*`, и во всех API-роутах трубы. Замок на плитке закрывает только визуальный путь.
- Переименование значения справочника, у которого есть студенты, ломает белый список. Решение: при переименовании значения переносить доступ на новое значение либо запрещать переименование когорт с привязанными студентами.

## 5. Модель данных

Черновик Prisma. Имена полей анкеты и карточки уточняются (раздел 11).

### 5.1 Правки существующих сущностей

```prisma
enum Role {
  ADMIN
  SUPERVISOR
  STUDENT
  EXPERT              // новое: внешний эксперт, без доступа к «Платформе ВКР»
}

enum NotificationType {
  // ... существующие значения
  EXPERT_REQUEST_NEW        // новый запрос — модератору
  EXPERT_REQUEST_APPROVED   // одобрен модератором — эксперту
  EXPERT_REQUEST_REJECTED   // отклонён модератором или экспертом — студенту
  EXPERT_REQUEST_ACCEPTED   // принят, контакты — студенту и эксперту
  EXPERT_FEEDBACK_REQUEST   // прошло 7 дней — обеим сторонам
}

model User {
  // ... существующие поля
  expert  ExpertProfile?
}
```

### 5.2 Карточка эксперта

Набор полей повторяет профиль научного руководителя (`SupervisorProfile`), с тремя отличиями: «Предлагаемые темы» заменены на «С какими темами могу помочь», поля про руководство проектами не переносятся, модерации карточки нет.

```prisma
model ExpertProfile {
  id              String   @id @default(cuid())
  userId          String   @unique
  user            User     @relation(fields: [userId], references: [id], onDelete: Cascade)

  workplace       String   @default("")   // Место работы (она же компания)
  position        String   @default("")   // Должность
  academicTitle   String   @default("")   // Учёное звание — у внешних экспертов может не быть
  academicDegree  String   @default("")   // Учёная степень — у внешних экспертов может не быть
  resumeUrl       String?                 // Ссылка на резюме или файл
  photoUrl        String?                 // Фото
  expertise       String[]                // Доменная экспертиза (теги) — по ней фильтр каталога
  helpTopics      String?                 // «С какими темами могу помочь» — опционально,
                                          // на месте proposedTopics у НР
  directions      String[]                // Направления студентов
  projectTypes    String[]                // Типы проектов
  contact         String   @default("")   // Контакт — виден только студенту с принятым запросом

  cardCompleted   Boolean  @default(false) // обязательные поля заполнены → в каталоге
  hiddenByOwner   Boolean  @default(false) // скрыл сам (отпуск)

  createdAt       DateTime @default(now())
  updatedAt       DateTime @updatedAt

  requests        ExpertRequest[]

  @@index([cardCompleted, hiddenByOwner])
}
```

**Чего в карточке нет.** Из профиля НР не переносятся `maxSlots` и `maxProjects` (про руководство проектом, не про консультацию) и `status` / `moderationComment` (карточка не модерируется). Из первоначальной постановки не берутся формат консультации и лимит запросов в месяц — по решению заказчика.

**ФИО** отдельным полем не дублируется — берётся из `User.name`: одна учётная запись, одно имя в обоих пространствах.

**Учёное звание и степень необязательны.** У НР они обязательны, но внешний эксперт из индустрии может не иметь ни того ни другого — поэтому здесь это поля со значением по умолчанию, а не обязательные.

**Обязательный минимум для попадания в каталог** (`cardCompleted = true`): место работы, должность, **резюме**, доменная экспертиза — хотя бы один тег, контакт. Резюме обязательно по решению заказчика: смысл раздела в том, что у эксперта подтверждённый опыт, и резюме — это подтверждение. Фото остаётся опциональным. Остальное тоже опционально.

Отсутствие резюме сервер отклоняет с ошибкой; остальные поля минимума проверяются на клиенте, а их отсутствие даёт `cardCompleted = false` — карточка сохранится, но в каталог не попадёт.

Условие показа в каталоге: `cardCompleted && !hiddenByOwner`. Два флага вместо одного нужны, чтобы различать «ещё не заполнил» и «заполнил, но скрыл»: сообщения пользователю в этих случаях разные.

**Дубль с профилем НР.** Фото, место работы, должность, звание, степень и резюме есть и в профиле НР, и в карточке эксперта. Иначе нельзя: у внешних экспертов профиля НР не существует вовсе. При подключении роли карточка предзаполняется из профиля НР, дальше правится отдельно и живёт своей жизнью.

### 5.3 Запрос на консультацию

```prisma
enum ExpertRequestStatus {
  NEW                     // Новый — ждёт модератора
  APPROVED_BY_MODERATOR   // Одобрен модератором — ждёт эксперта
  REJECTED_BY_MODERATOR   // Отклонён модератором (терминальный)
  REJECTED_BY_EXPERT      // Отклонён экспертом (терминальный)
  CONTACTS_SENT           // Контакты отправлены
  AWAITING_FEEDBACK       // Ожидает обратной связи
  CLOSED                  // Закрыт
}

model ExpertRequest {
  id                String   @id @default(cuid())
  studentId         String
  student           StudentProfile @relation(fields: [studentId], references: [id], onDelete: Cascade)
  expertId          String
  expert            ExpertProfile  @relation(fields: [expertId], references: [id], onDelete: Cascade)

  // Анкета
  topic             String   // что хочу обсудить (порог по длине — см. 11)
  expectedResult    String   // какой результат жду от встречи
  ownProgress       String   // что уже сделал сам

  // Снимок профиля на момент запроса: курс и программа со временем меняются,
  // а модератор и эксперт должны видеть то, что было при отправке
  directionSnapshot String
  courseSnapshot    Int

  status            ExpertRequestStatus @default(NEW)
  moderatorComment  String?  // причина отклонения — обязательна при REJECTED_BY_MODERATOR
  expertComment     String?  // причина отказа эксперта

  moderatedById     String?
  moderatedAt       DateTime?
  acceptedAt        DateTime?
  contactsSentAt    DateTime?  // точка отсчёта 7 дней
  feedbackRequestedAt     DateTime?
  feedbackReminderSentAt  DateTime?
  closedAt          DateTime?
  closedWithoutFeedback Boolean @default(false) // закрыт джобой, а не студентом (08.20)

  createdAt         DateTime @default(now())
  updatedAt         DateTime @updatedAt

  feedbacks         ExpertRequestFeedback[]

  @@index([status])
  @@index([expertId, status])
  @@index([studentId])
  @@index([status, contactsSentAt])       // для джобы 7 дней
  @@index([status, feedbackRequestedAt])  // для джобы напоминания
}
```

Требование 08.18 выполняется конструктивно: экспертные запросы — отдельная сущность `ExpertRequest`, существующая модель `Application` не затрагивается, ни один список не объединяет их.

### 5.4 Обратная связь

```prisma
enum FeedbackAuthorSide {
  STUDENT
  EXPERT
}

model ExpertRequestFeedback {
  id          String   @id @default(cuid())
  requestId   String
  request     ExpertRequest @relation(fields: [requestId], references: [id], onDelete: Cascade)
  authorSide  FeedbackAuthorSide

  metHappened Boolean          // состоялась ли встреча
  rating      Int?             // 1–5, только от студента
  comment     String?

  createdAt   DateTime @default(now())

  @@unique([requestId, authorSide])   // по одному ответу с каждой стороны
  @@index([requestId])
}
```

Имя намеренно не `Feedback` — эта модель в схеме уже занята тикетами поддержки.

Два ответа на один и тот же вопрос «встреча была?» дают честную метрику 08.19: ответа только студента недостаточно, потому что при сорвавшейся встрече студенты такие формы не заполняют.

**Три категории в метрике конверсии**, а не две:

- *встреча состоялась* — есть подтверждение хотя бы одной стороны;
- *встреча не состоялась* — есть ответ, и он отрицательный;
- *нет данных* — запрос закрыт джобой без ответа студента (`closedWithoutFeedback = true`).

Смешивать третью категорию со второй нельзя: молчуны систематически занизят конверсию, и метрика перестанет отражать реальность.

### 5.5 Открытые когорты

```prisma
model ExpertPipelineCohortAccess {
  id        String   @id @default(cuid())
  cohort    String   @unique   // значение из справочника cohorts
  isOpen    Boolean  @default(false)
  updatedAt DateTime @updatedAt
}
```

Отдельная таблица вместо записи в общих настройках — проще индексировать, проще смотреть историю и не надо парсить JSON при каждой проверке доступа.

## 6. Статусная машина

| Из | Кто переводит | В | Условия и эффекты |
|----|---------------|---|-------------------|
| — | Студент | `NEW` | Когорта открыта, анкета валидна, к этому эксперту нет нерассмотренного запроса. Уведомление модератору |
| `NEW` | Модератор | `APPROVED_BY_MODERATOR` | Уведомление эксперту |
| `NEW` | Модератор | `REJECTED_BY_MODERATOR` | Причина обязательна. Уведомление студенту с причиной. Терминальный |
| `APPROVED_BY_MODERATOR` | Эксперт | `CONTACTS_SENT` | Принятие и отправка контактов — один переход в одной транзакции. `acceptedAt`, `contactsSentAt`. Обмен контактами |
| `APPROVED_BY_MODERATOR` | Эксперт | `REJECTED_BY_EXPERT` | Уведомление студенту. Терминальный |
| `CONTACTS_SENT` | Система (джоба) | `AWAITING_FEEDBACK` | `contactsSentAt + 7 дней`. Формы обеим сторонам, `feedbackRequestedAt` |
| `AWAITING_FEEDBACK` | Студент | `CLOSED` | Ответ студента получен, `closedAt` |
| `AWAITING_FEEDBACK` | Система (джоба) | `CLOSED` | `feedbackRequestedAt + 7 дней`, ответа студента нет. `closedWithoutFeedback = true`. Уведомления не отправляются |

**Права на переходы.** Модератор — только `ADMIN`. Решение по запросу — только эксперт, которому запрос адресован (сверка `expertId` с `ExpertProfile` текущего пользователя, не с `userId`). Закрытие — только студент-автор запроса.

**Что видит эксперт до принятия:** анкету, имя студента и его программу. Контакты студента не показываются.

**Что видит студент:** свои запросы со статусами, причину отклонения модератора или эксперта, контакты эксперта — только после принятия.

In-app — через существующий `notify()` / `notifyMany()`, email — через `sendMail()`. Модераторов может быть несколько: рассылка по всем пользователям с ролью `ADMIN`.

Все ссылки в уведомлениях ведут внутрь `/expert/*` напрямую, минуя экран выбора (08.04).

### 8.1 Привязка уведомлений к пространству (08.22)

Уведомления двух пространств не смешиваются: счётчик в сайдбаре и список на странице показывают только то, что относится к пространству, в котором человек находится. На переключателе пространств — бейдж «есть непрочитанные в другом пространстве», чтобы ничего не потерялось.

Пространство **не хранится в модели** `Notification` и миграция не нужна — оно вычисляется из типа уведомления: все значения `EXPERT_*` относятся к трубе, остальные к платформе. Достаточно функции-маппинга, параметра пространства в `GET /api/notifications` и фильтра на странице.

Оговорка на будущее: при добавлении новых значений в `NotificationType` их нужно явно относить к пространству. Дефолт для незнакомого типа — платформа, чтобы уведомление не потерялось.

Фактически разделение заметят только научный руководитель с ролью эксперта и админ: у студента и у внешнего эксперта уведомления всегда из одного пространства.

## 9. Отложенные задачи

Повторяем существующий паттерн `app/api/events/reminders/route.ts`: POST-роут, защищённый `CRON_SECRET`, вызывается с сервера по расписанию.

`POST /api/expert/jobs/feedback?secret=...` — два прохода за один вызов:

1. **Сбор обратной связи.** Запросы в `CONTACTS_SENT` с `contactsSentAt <= now - 7 дней` → `AWAITING_FEEDBACK`, формы студенту и эксперту, `feedbackRequestedAt = now`.
2. **Напоминание.** Запросы в `AWAITING_FEEDBACK` с `feedbackRequestedAt <= now - 3 дня`, без ответа студента и с пустым `feedbackReminderSentAt` → одно напоминание, `feedbackReminderSentAt = now`.
3. **Авто-закрытие.** Запросы в `AWAITING_FEEDBACK` с `feedbackRequestedAt <= now - 7 дней` и без ответа студента → `CLOSED`, `closedWithoutFeedback = true`, `closedAt = now`. Уведомления не отправляются. Ответ эксперта, если он есть, сохраняется и учитывается в метрике.

**Таймлайн запроса после принятия:** контакты отправлены → +7 дней форма обратной связи → +3 дня напоминание студенту → +7 дней от формы авто-закрытие. У студента есть 4 дня после напоминания.

Идемпотентность обеспечивают сами отметки времени: повторный вызов в тот же день ничего не задублирует. Джоба безопасна при пропуске дня — просто догонит накопившееся.

Запуск: запись в crontab прод-сервера, раз в сутки, рядом с ночными бэкапами.
